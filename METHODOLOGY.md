# Методика разворачивания фреймворка убийства гипотез
# Atropos — Hypothesis-Killing Framework — Deployment Methodology

Переносимый (portable) документ: как развернуть фреймворк «убийства гипотез» (hypothesis killing) в любом проекте, работающем с гипотезами и данными. Документ самодостаточен — аналитик или ИИ-агент без контекста разворачивает всё с нуля только по нему. Значения конкретного проекта обозначены плейсхолдерами: `[PROJECT_ROOT]`, `[DATA_DIR]` и т.п.

Суть фреймворка: каждая гипотеза проходит пайплайн (pipeline) из 7 стадий с заранее заданными kill-критериями. Возможные исходы: `KILLED` (убита — на кладбище/graveyard), `SURVIVED` (выжила — может обосновывать решение), `INCONCLUSIVE` (недостаточно данных — переоткрытие на новом снимке).

---

## 1. Предварительные требования (Prerequisites)

Минимально необходимая инфраструктура данных:

- **Каталог данных** `[DATA_DIR]` с версионируемыми снимками (snapshots): состояние данных фиксируется на дату `[SNAPSHOT_DATE]` и далее не изменяется.
- **Воспроизводимый источник** `[DATA_SOURCE]` (БД, файлы, API): запрос или выгрузка сохраняется в текстовом виде рядом со снимком.
- **Словарь данных** (data dictionary): поля, единицы измерения, период покрытия. Без него kill-критерии неизмеримы.
- **Git-репозиторий** `[PROJECT_ROOT]`: все артефакты гипотез коммитятся, история append-only.
- **Python 3.11+** с возможностью создавать виртуальные окружения.

Ничего сверх этого не требуется: фреймворк не зависит от стека БД, облака или платных инструментов.

## 2. Структура каталогов (Directory Structure)

Создать в `[PROJECT_ROOT]`:

```text
[PROJECT_ROOT]/
├── docs/
│   └── HYPOTHESIS_KILLING_FRAMEWORK.md   # главный документ методологии
├── hypotheses/
│   ├── preregistrations/                  # H-NNNN: пререгистрации (до данных)
│   ├── code/                              # H-NNNN: код тестов
│   ├── graveyard/                         # H-NNNN: надгробия (вердикты)
│   └── INDEX.csv                          # реестр всех гипотез
├── data/                                  # [DATA_DIR]
│   ├── snapshots/                         # снимки: snapshots/[SNAPSHOT_DATE]/
│   └── DATA_DICTIONARY.md                 # словарь данных
├── tests/                                 # pytest-тесты кода гипотез
├── scripts/                               # линтеры и утилиты реестра
├── pyproject.toml                         # зависимости (uv), конфиг ruff/mypy/pytest
└── AGENTS.md, CLAUDE.md                   # инструкции агентов (шаблоны в комплекте)
```

Ключевое правило: одна гипотеза = один идентификатор `H-NNNN` = минимум три артефакта: prereg, code, tombstone.

## 3. Окружение Python (Python Environment)

Менеджер пакетов — **uv** (быстрый, воспроизводимый, lock-файл в коммите):

```bash
cd [PROJECT_ROOT]
uv python pin 3.12                # зафиксировать версию интерпретатора
uv init --package                 # создаст pyproject.toml со структурой пакета
uv add numpy pandas scipy         # рантайм-зависимости
uv add --dev pytest ruff mypy     # инструменты разработки
uv sync                           # создать .venv и поставить всё по uv.lock
```

Все команды дальше — через `uv run` (например `uv run pytest`), активация окружения не нужна.

Минимальный стек: `numpy` (вычисления), `pandas` (данные), `scipy` (статистика), `pytest` (тесты), `ruff` (стиль: 78 колонок, докстринги, perflint, E741 — конфигурация в `pyproject.toml`), `mypy` (типы: режим strict). Расширять только по необходимости; версии фиксируются в `uv.lock` автоматически.

## 4. Пошаговое разворачивание (Step-by-Step Deployment)

| Шаг | Действие | Результат |
|-----|----------|-----------|
| 1 | Создать структуру каталогов (раздел 2) | Пустой скелет закоммичен в git |
| 2 | Настроить окружение Python (раздел 3) | `pyproject.toml` + `uv.lock` закоммичены |
| 3 | Зафиксировать первый снимок данных и словарь | `[DATA_DIR]/snapshots/[SNAPSHOT_DATE]/` готов |
| 4 | Написать `docs/HYPOTHESIS_KILLING_FRAMEWORK.md` | 7 стадий, 6 законов, форматы prereg и tombstone |
| 5 | Заполнить `AGENTS.md` и `CLAUDE.md` (заменить плейсхолдеры) | Инструкции агентов без незаменённых `[PLACEHOLDER]` |
| 6 | Провести пилотную гипотезу `H-0001` по полному циклу | Tombstone в graveyard + строка в INDEX.csv |
| 7 | Закоммитить всё, назначить владельца `[OWNER]` | Фреймворк активен |

Пилот `H-0001` берётся заведомо убиваемым: цель шага — проверить механику кладбища, а не получить выжившую гипотезу.

## 5. Интеграция в CI/CD (CI/CD Integration)

Обязательные проверки на каждый pull request — транслируются в любой CI (GitHub Actions, GitLab CI, Jenkins и т.д.):

1. `uv run ruff check .` и `uv run ruff format --check .` — стиль кода (78 колонок, докстринги, perflint, E741), ноль предупреждений.
2. `uv run mypy` — строгая типизация (strict), ноль ошибок.
3. `uv run pytest -q` — юнит-тесты; код гипотезы без теста CI не пропускает.
4. Линтер пререгистраций `scripts/lint_preregistrations.py` (около 20 строк на Python): каждый `preregistrations/H-*.md` обязан содержать ID, фальсифицируемое предсказание (falsifiable prediction), числовой kill-критерий, снимок, seed, автора, дату.
5. Сверка `hypotheses/INDEX.csv` с каталогом graveyard: у каждой гипотезы с tombstone есть строка реестра.

Пример для GitHub Actions (сокращённо):

```yaml
- run: uv run ruff check .
- run: uv run ruff format --check .
- run: uv run mypy
- run: uv run pytest -q
- run: python scripts/lint_preregistrations.py
```

Опционально: ночная задача (nightly job), пересчитывающая все `SURVIVED`-гипотезы на новом снимке данных, — проверка, что выжившие не умерли на свежих данных.

## 6. Обучение аналитика или агента (Onboarding)

Протокол ввода в работу (30–60 минут), по порядку:

1. Прочитать `docs/HYPOTHESIS_KILLING_FRAMEWORK.md` — пайплайн и законы.
2. Прочитать `AGENTS.md`; Claude-совместимым агентам — также `CLAUDE.md`.
3. Прочитать 3–5 случайных надгробий из `graveyard/` — как формулируются kill-критерии и вердикты.
4. Просмотреть `INDEX.csv` — какие классы гипотез уже закрыты.
5. Пилот: провести учебную гипотезу (префикс `H-TRAIN-*`) до надгробия под присмотром наставника.

Критерий готовности: новичок самостоятельно оформляет пререгистрацию, проходящую линтер, без подсказок.

## 7. Масштабирование (Scaling)

- **10 гипотез.** Плоские файлы и ручное ведение `INDEX.csv`. Достаточно дисциплины именования `H-NNNN`.
- **100 гипотез.** Обязательный graveyard check перед каждой новой гипотезой — поиск по тегам, а не по заголовкам; теги `[TAGS]` обязательны в пререгистрации; WIP-лимит — не более `[WIP_LIMIT]` открытых гипотез на аналитика.
- **1000 гипотез.** Автоматизация: скриптовый поиск по реестру, кластеризация по тегам, батчи (один тестовый скрипт — семейство родственных гипотез), периодический отчёт «доля KILLED/SURVIVED по классам». Главная угроза — дублирование, поэтому каждый новый класс гипотез сначала ищется на кладбище.

Правило масштаба: с ростом числа гипотез стоимость graveyard check должна падать (за счёт автоматизации), а не расти.

## 8. Типичные ошибки (Common Pitfalls)

| Ошибка | Симптом | Лекарство |
|--------|---------|-----------|
| Пост-хок сдвиг критериев (criterion drift) | Kill-критерий «уточняется» после взгляда на данные | Коммит prereg до выгрузки; линтер; закон 5 |
| Воскрешение убитой (resurrection) | Та же гипотеза под новым названием | Graveyard check по тегам и структуре, не по заголовку |
| Нефиксированный seed | Тест невоспроизводим | Seed — обязательное поле пререгистрации (закон 3) |
| Сдвиг снимка данных | Тест считает на другом snapshot, чем заявлено | ID снимка и в prereg, и в коде теста |
| Вердикт-инфляция (verdict inflation) | На кладбище попадают только чужие гипотезы | CI-сверка INDEX.csv с preregistrations/ |
| Пропуск кладбища «по памяти» | Растут дубликаты | Graveyard check — стадия пайплайна, а не привычка |
| Пилот на реальных данных | Мусор в реестре | Префикс `H-TRAIN-*` и отдельный каталог |

## 9. Критерии готовности (Definition of Done)

- [ ] Структура каталогов из раздела 2 существует и закоммичена.
- [ ] `pytest`, `ruff` и `mypy` проходят локально и в CI.
- [ ] Линтер пререгистраций работает и ловит пустые kill-критерии.
- [ ] Пилотная `H-0001` прошла полный цикл и лежит на кладбище.
- [ ] `AGENTS.md` и `CLAUDE.md` заполнены — ни одного незаменённого `[PLACEHOLDER]`.
- [ ] Новый аналитик проходит онбординг (раздел 6) без посторонней помощи.

## Приложение A. Шаблон пререгистрации (Preregistration Template)

```markdown
# H-[NNNN]: [TITLE]
- Автор: [AUTHOR], дата: [DATE], теги: [TAGS]
- Prediction: [MEASURABLE_FALSIFIABLE_PREDICTION]
- Kill criteria: [METRIC] < [THRESHOLD] на снимке [SNAPSHOT_DATE], seed [SEED]
- Graveyard check: [WHAT_WAS_SEARCHED], результат: [FOUND_NOTHING | DUPLICATE_OF_H-XXXX]
```

## Приложение B. Шаблон надгробия (Tombstone Template)

```markdown
# H-[NNNN] — [KILLED | SURVIVED | INCONCLUSIVE]
- Вердикт: [VERDICT], дата: [DATE], автор: [AUTHOR]
- Метрика: [ACTUAL_VALUE] против порога [THRESHOLD] (снимок [SNAPSHOT_DATE])
- Причина: [ROOT_CAUSE]; урок: [LESSON]; не пробовать снова: [DO_NOT_RETRY]
```
